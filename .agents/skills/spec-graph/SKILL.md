# Spec graph

来源：受 [ThinkRail](https://github.com/JetBrains/thinkrail) 的 `writing-specs` 和 `spec-graph` 启发。

使用普通文件工具，维护长期有效的产品目标、架构、模块契约、边界和决策。

## 范围

- 仅按本次请求操作；查看、检查保持只读。
- 不规定开发流程，不要求每次编码前调用，不自动创建任务计划。
- 不修改业务代码或 agent 配置，完成请求后结束。

## 节点格式

节点是一份带 YAML frontmatter 的 Markdown 文件：

```yaml
---
id: auth
type: module-design
title: 身份认证模块
status: draft
---
```

必填字段为 `id`、`type`、`title`。`id` 在项目内唯一且稳定。

常用类型：

- `goal-and-requirements`：产品目标与范围。
- `architecture-design`：系统结构、跨模块决策与不变量。
- `module-design`：模块职责、契约与边界。
- `submodule-design`：子模块职责、契约与边界。

可选字段：

- `parent`：上级节点 ID，不可循环。
- `depends-on`：依赖节点的 ID 列表。
- `references`：相关规范的 ID 列表，允许相互引用。
- `implements`：所实现目标或契约的 ID 列表。
- `status`、`tags`：状态和分类。

链接只引用已有或本次将创建的节点。无依据的字段省略。沿用项目已有格式和扩展字段，不强制迁移。规范文件是持久载体，图由链接派生，无需另建数据库或索引。

## 写作原则

- 一个节点对应一个真实职责、边界或独立决策，不按目录机械生成。
- 写清意图、契约、约束和决策原因，避免复述代码或填充占位章节。
- 相同事实记录一次，其余引用，避免重复和矛盾。
- 区分已确认要求、当前实现和推断；不确定内容在对应位置标明。
- 从代码观察到的行为不自动等于预期行为，不将 bug 写成约定。
- 新推断规范使用 `draft`；已确认的长期规范可使用 `active`，不因一次任务完成而改为 `done`。
- 规范与实现冲突时指出差异，不静默认定任意一方正确。
- 任务清单、实施步骤和临时讨论不自动纳入长期规范。

## 按请求操作

根据请求选择操作，无需执行全部步骤：

- **建立**：读取相关文档和必要代码，复用已有规范，按真实边界创建最少的节点，只添加有依据的关系。
- **查看**：定位节点，按需展示父级、子级、依赖或引用。默认使用紧凑列表，需要图示时再生成 Mermaid。
- **修改**：保留无关正文、元数据和现有路径。用户要求改 ID、移动或删除节点时，同步处理引用。
- **检查**：核对必填字段、字段类型、重复 ID、悬空链接、parent 循环，以及已读取内容中的明显矛盾。

项目规范位于 `docs/specs/`，新增规范也放在该目录；不强求固定文件名或完整层级。已有设计文档可原地纳入图，避免复制。

只询问会实质影响规范且资料无法回答的问题，其余疑问标为推断。检索避开依赖、构建产物和缓存，不加载无关正文。

## 检查与交付

编辑后检查受影响的结构；判断链接是否存在时可读取范围外节点的元数据。发现依赖循环时说明实际关系，不自动删边。

使用现有工具，不安装额外依赖。明确说明无法可靠检查的部分；局部检查不能称为全图通过，结构正确不代表代码符合规范。

简要报告节点和关系的变化、检查结果及未确认的推断。除非用户要求，不额外生成报告、索引或其他产物。
